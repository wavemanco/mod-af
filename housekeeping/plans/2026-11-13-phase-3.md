# housekeeping Phase 3 plan

Phase 3 adds `audit`, `owed`, the automatic parts, the notes for `loose-ends`, `route` and `decide`, and the README
and marketplace entry (DESIGN 3.9, 3.10, 3.11, section 6; backlog rows HK-002 to HK-005). It follows the
Elephant-Goldfish model: a brainstorm by seven read-only lenses (`research/phase-3-concepts-brief.md`), this
draft, a review loop by fresh lenses, then the build. The owner asked on 2026-11-13 for no stop-and-ask in this
phase: "deal with things autonomously". So every question the brief left open is settled below with its default,
recorded as Claude's call with the options rejected, and listed in DESIGN section 10 for the owner to check.

## Stop rules for the build

- No agent starts a live session, pushes, opens a PR or publishes. The controller pushes after the gate.
- No change to `version: 1` in the settings, to the agent-guide line, or to the "How this file is kept" heading.
- Survey's and plan's procedure text and keep sentences stay byte for byte.
- A fix larger than its task is not widened: the agent stops it, says why, and goes on.

## How the build runs

Five tasks in order, each by one agent on `housekeeping/phase-3`, cut from main at the Phase 2 merge. Tasks share
`hooks/register.tsx`, so they never run at once. Each change gets a focused test that fails before it; the full
gate runs at the end of each task (`claude plugin test housekeeping`, the Node specs with TEMP set to a scratch
folder, `claude plugin validate housekeeping`). One commit per item. The engine's hook types are in the scratch
copy the controller hands each agent; nothing an agent relies on from them is assumed without a kit test.

### Task 1: fix what is built first

Files: `hooks/register.tsx`, `hooks/core/brief.ts`, `hooks/core/templates.ts`, `hooks/core/findings.ts`, a new
`hooks/core/card.ts`, a new `hooks/core/commands.ts`, `cli.ts`, `prompts/*.md`.

- **Per-procedure keep text.** Each prompt file carries its keep sentence between markers
  (`<!-- keep -->` ... `<!-- /keep -->`); `keep()` quotes the sentence of each procedure sent. The record holds
  only the procedures in an explicit list, by name. Survey's and plan's kept text unchanged, pinned.
- **The prompt hand-over is split from the survey's inventory** (`handPrompt(name, context)`): survey and plan
  keep the inventory and the walk; audit and owed get only what they need.
- **The records card.** A pure function of the settings: the two paths, the commit test, the columns, the ID
  patterns with the next free ID, the not-doing heading or "none set", the decisions folder or "none set", and
  four fixed lines: a trigger is a step, never a date, never "Every" unless the work recurs; a decision updates
  its row; read rows by ID, never a whole file; run `/housekeeping check` after filing. Served as its own
  prompt.context block where `.housekeeping.json` exists, even while the view is being built, and printed by
  `cli.ts brief` after the brief.
- **Duties at serve time.** `dutyDue` exported; the stored view keeps the duties; the "Duties due" line is
  worked out when the view is served, as the branch line is. A stored view with no duties field is a miss.
- **A view-format constant in the stamp,** so an upgrade or a rollback rebuilds once.
- **One command table** (`core/commands.ts`) feeding the usage line, the command description, the argument hint,
  the time-out mapping and `cli.ts`'s list.
- **init:** `## Not doing` in the playbook template, `notDoing` and `decisions` keys; `check` recommends them where
  missing.

### Task 2: `owed`

Files: a new `hooks/core/owed.ts`, `hooks/adapter.ts`, `cli.ts`, `hooks/register.tsx`, `FORMAT.md`.

- A pure core function of the rows at base and head, the changed paths, the added and removed lines outside the
  records and the settings, and the commit messages from base to head. It lists, grouped by action and each with
  its evidence (the trigger word and the path or line it matched, the commit that names the row): rows whose
  Trigger fired, rows the commits name, the checklist lines that name those rows. Rows the branch already
  settled are listed apart. IDs the branch adds that the base already holds are reported.
- Reading: the records at both refs by `git show`, with `--end-of-options`; no history walk; a cut-short stream
  stops it; no local main and shallow clones give their own messages.
- On the plugin route each changed path is put to the Read rules first; a denied path is excluded and counted.
- `/housekeeping owed [--base <ref>] [--head <ref>]` and `node cli.ts owed --base <ref> [--head <ref>]`; exit 0;
  on main with no base, the reply says to give one. The output is masked.
- FORMAT gets the code-name rule (call 13).

### Task 3: `audit`

Files: a new `prompts/audit.md`, `hooks/register.tsx`, `templates.ts` (the duty row in init's playbook),
`README.md` line 5.

- The procedure: the starting sha from the audit duty row (call 2); tier 0, which costs no tokens (checklist
  lines ready to tick, doors just opened, rows gone with no Done entry); tier 1, `owed` over the range plus the IDs
  main's messages name, strongest evidence first, at most 25 pairs per run with the rest counted; then only those
  diffs read. A fresh subagent that is not a fork checks each batch of about 10 proposals; with none, every case
  is a judgement call. Clear-cut means a closing word, the change still present at main's tip, and the skeptic's
  agreement. Applying: a branch from main in a clean tree, one commit per change, Done rows in the file's own
  shape, the duty row's Last done updated, then `check` with closed up and open down by the same count and no
  new gone rows. Judgement calls get a dated "Audit YYYY-MM-DD:" line and a "Default until decided:" line in the
  row. Where the repository's rules restrict writes, everything is a judgement call (call 11).
- `/housekeeping audit` hands the procedure with `owed`'s data over the range; it has no Node form, and the
  time-out reply says so.

### Task 4: the automatic parts

Files: `hooks/register.tsx`, `.claude-plugin/plugin.json` (`userConfig`), a new `hooks/core/delta.ts` if needed.

- **Compaction:** where `.housekeeping.json` exists, the summary is asked to keep, under one fixed heading, one line
  per item not yet written into the two files in this conversation, decisions word for word, at most 40 lines
  (call 6). Built apart from the procedure paragraph, so a failure in one cannot lose the other; fails open.
- **After a commit or a pull, seen on the Bash and PowerShell tools:** only where the result has a git operation
  or the command holds `git`; a try/catch inside, `next` called once, the original result returned. If main's sha
  moved and the two files changed between the old and new sha, the rebuild starts without waiting, the page is
  written from the same walk, and a delta of at most 400 characters is attached to main-loop results only.
- **At the main loop's turn end:** publish per the cadence (call 7), only to a link already stored, only in an
  interactive session with the Artifact tool allowed, only when the page changed; suggest `/loose-ends` to the
  person when three or more commits since the last records commit, or after a compaction that kept items (no
  suggestion while either file has uncommitted edits); write the catch-up record when it changed: ids, counts
  and shas only, a bounded list keyed by session.
- **The first prompt.context of a new conversation** (and after `/clear`) offers `claude --resume <id>`, then
  `/loose-ends`, once per ended session that armed it (call 5); not for a resume of the same id, nor for runs
  that were not interactive.
- **Session start:** a stale-map line when the stored link's sha and main differ on the two files.
- **Debug lines:** one masked line per firing (call 15).
- Every new hook that gates has its own failure path; none can run a command twice or stop a spawn, a
  compaction or a commit.

- `INTEGRATION.md`: for each of loose-ends, route and decide, which file it reads, what the card tells it, and

- The README by command, with a section on what runs on its own, when it fires, what it costs and how to turn it

- DESIGN: 3.8 and 3.10 brought up to what is built, "keeps" made "is asked to keep", section 10 gets the calls

- `plugin.json` version bumped; the marketplace description edited last.
- `research/live-checks.md`: the owner's sitting, folded into HK-080, with each check's keystrokes and the one
  observation that means pass.
- BACKLOG: HK-002 to HK-005 to Done, HK-003 reworded, HK-077's trigger noted as fired, rows for what is filed.

## Not built in Phase 3

Filing after every commit (the owner's choice); hooks on the siblings' commands; the HK-077 hook; `cli.ts audit`;
an incremental history cache; a per-repository cadence.

## Completion criteria

- Each task's items have their tests, or a reason in the task's result.
- The gate passes after the last task, and the reference repository's `check` gives the same findings as before.
- The name and word searches over the branch find nothing.
- A narrow check runs over the branch before it goes to the owner; the PR waits for the owner.
