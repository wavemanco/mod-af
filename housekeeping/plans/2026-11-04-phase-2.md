# housekeeping Phase 2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for
> tracking.

**Goal:**
- Close the 37 fixes that Phase 1's reviews filed for Phase 2 (`BACKLOG.md` rows HK-006 to HK-042).
- Build `survey` and `plan`: an inventory any repository's files can be checked against, and the two
  procedures an agent follows to move a repository's scattered pending work into the pair of files.
- Prove them by dry runs on clones of test repositories A, B and C.

**Architecture:**
- **The inventory is computed.** A pure core module scores every tracked text file for signs of pending
  work, counts the references to the likely trackers, flags the machine readers among them, and collects
  what the guide files say.
- **The judgement is the agent's.** The agent follows a procedure, shipped as a Markdown prompt: which file
  is canonical, what is history, how items become rows, which of the repository's own rules constrain
  the move.
- **The callers.** The plugin's `/housekeeping survey` and `/housekeeping plan` hand the agent the procedure
  and the inventory as context, as `loose-ends` hands over its procedure. The Node command prints the same
  inventory.

**Tech stack:** as Phase 1: TypeScript run by Node 24 and by the Claude Code plugin engine; tests through
`claude plugin test` (`claude-code/testing`) and `node --test`; no npm dependencies.

**Spec:** [`../DESIGN.md`](../DESIGN.md), approved 2026-11-03. The sections that bind this plan are 3.8, 6
(Phase 2), 7 (Phase 2) and 8. The fixes' details are in [`../BACKLOG.md`](../BACKLOG.md), one row per
fix.

## Global Constraints

- **Everything in Phase 1's Global Constraints still holds** ([`2026-11-03-phase-0-1.md`](2026-11-03-phase-0-1.md)).
  That covers:
  - no repository named in a committed file;
  - the core imports no `node:*` module and nothing from `claude-code` except types;
  - type-strippable syntax only, with `.ts` on imports;
  - writes go through the Write tool, apart from the page;
  - ASCII, a deterministic page, privacy;
  - the gate: `claude plugin test housekeeping`, then `node --test housekeeping/node-tests/*.spec.ts`, then
    `claude plugin validate housekeeping`.
- **The name search** uses the Grep tool with the words in `research/raw/names.txt`. The Bash
  `grep -f` crashes on this machine.
- **The survey writes nothing** in the repository it surveys (DESIGN 3.8).
- **The plan's steps are applied only after approval,** on a branch, one commit per step, split the way the
  repository's own guards require, with the repository's own tests run before and after (DESIGN 3.8).
- **Dry runs:**
  - They work only in full clones under the session's scratch folder, with short folder names (`a2`, `b2`,
    `c2`).
  - Nothing is ever pushed from them. The clones are deleted at the end of Phase 2.
  - Their full reports, which may name the repositories, go to `research/raw/` (git-ignored).
  - Only pass or fail, in described terms, is committed (`research/phase-2-results.md`).
  - A dry-run agent stands in for the owner: it records each question the plan asks as a question, makes
    a provisional choice so the run can go on, and lists both in its report.
- **Test repository B pins its package manager's version.** Run its commands with that version, not with the
  one installed here.
- **Test repository A's suite needs its install step, which uses the network.** Both suites run before and after
  on the same machine, and a difference that the plan's change does not plainly explain is stop rule 5.
- **Never publish an artifact.** A `claude -p` run carries `--disallowedTools Artifact`,
  `MSYS_NO_PATHCONV=1`, `C:/…` paths, and `--plugin-dir` for housekeeping, loose-ends, route and decide.

## Review Focus

1. **A large repository** (thousands of files, big generated files, lockfiles, binaries): the survey caps
   what it reads, says what it skipped, and finishes. The test is in Task 6.
2. **A file that looks like a tracker but is history** (a dated note, a log that is never edited): it is
   flagged as likely history, not proposed as canonical. The test is in Task 6.
3. **A file that is not UTF-8 text:** it is skipped without a crash, and counted as skipped. The test is in
   Task 6.
4. **A reference from code, a test or a script** (a machine reader) is told apart from a mention in prose,
   because renaming would break it. The test is in Task 6.
5. **A repository with nothing to move** (empty, or no candidates): the survey says so and offers `init`.
   The tests are in Tasks 6 and 8.

### Task 6: the survey's inventory

**Files:**
- Create: `hooks/core/survey.ts` and `tests/survey.test.ts`.
- Modify: `hooks/adapter.ts` (`readTracked`), `cli.ts` (a `survey` subcommand) and `node-tests/cli.spec.ts`.

**Interfaces:**
- Produces, in `survey.ts` (pure):

```ts
export type SurveyFile = { path: string; text: string }
export type Signals = { name: boolean; idHeadings: number; idTables: number; openBoxes: number;
  doneBoxes: number; todos: number; statusWords: number; dated: boolean; guide: boolean }
export type Candidate = { path: string; signals: Signals; score: number;
  hint: 'likely-tracker' | 'maybe' | 'likely-history' }
export type Reference = { target: string; from: string; count: number; machine: boolean }
export type Inventory = { files: number; candidates: Candidate[]; references: Reference[];
  guides: { path: string; line: number; text: string }[]; skipped: { path: string; why: string }[] }
export function inventory(files: SurveyFile[], skipped?: { path: string; why: string }[]): Inventory
export function formatInventory(inv: Inventory, maxChars?: number): string   // default 20,000
```

- Produces, in `adapter.ts`:
  `readTracked($, root): Promise<{ files: SurveyFile[]; skipped: { path: string; why: string }[] }>`.
  It runs `git ls-files -z`, then reads each file with `$.fs.read`.
  - It skips lockfiles (`*.lock`, `pnpm-lock.yaml`, `package-lock.json`), anything over 512 KB, and any
    text holding a NUL character.
  - It stops at 3,000 files or 30 MB in all, and says so in `skipped`.
- `cli.ts` gets the same reader (node:fs and git), and
  `node housekeeping/cli.ts survey [--repo <dir>] [--json]`.

**Rules for `inventory`:**
- **`name`:** the base name matches
  `/backlog|todo|roadmap|plan|open|pending|defer|follow.?up|checklist|docket|tracker|playbook|issues|tasks|progress|launch/i`.
- **`idHeadings`:** headings of the form `^#{2,4}\s+[A-Z][A-Z0-9]*-?\d+\b`.
- **`idTables`:** tables whose first header cell is `ID`, `Id`, `#`, `Key` or `Ref`, using `scanTables`.
- **Boxes:** `openBoxes` counts `- [ ]` lines and `doneBoxes` counts `- [x]` lines.
- **`todos`:** `TODO`, `FIXME` or `XXX` in files that are not Markdown.
- **`statusWords`:** the words OPEN, DEFERRED, PENDING, BLOCKED, PARKED, TRIGGER, FIRED, CLOSED and DONE, as
  whole words, case-sensitive.
- **`dated`:** a date `\d{4}-\d{2}-\d{2}` in the path.
- **`guide`:** the base name is `README`, `CLAUDE`, `AGENTS`, `CONTRIBUTING` or `GOAL`, any extension.
- **`score`:** `3*name + 2*idHeadings + 2*idTables + openBoxes + statusWords/5 + todos/10`.
- **Candidates:** every file with a score of at least 3, sorted by score (ties by path).
  - The hint is `likely-history` when `dated` is set, or when the path has a folder named like
    `archive`, `history`, `log`, `logs`, `passes` or `responses`.
  - Otherwise it is `likely-tracker` when the score is at least 10, else `maybe`.
- **References:** for each of the top 15 candidates, every other file that names its path or its base
  name, with counts. `machine` is set when the referring file is not Markdown.
- **Guides:** the lines of guide files that say "backlog", "source of truth", "single", "defer",
  "pending", "trigger" or "docket", each cut to 200 characters.

### Task 7: the `survey` and `plan` procedures

**Files:**
- Create: `prompts/survey.md` and `prompts/plan.md`.
- Modify: `hooks/register.tsx` (the `survey` and `plan` arguments), `tests/plugin.test.ts`, `README.md`
  and `FORMAT.md`.

**Interfaces:**
- `/housekeeping survey` returns:
  - `{ text: 'housekeeping survey: <n> files read, <m> candidates', context: [<prompts/survey.md>, formatInventory(inv)] }`;
  - the procedure is read with `$.fs.read(`${$.plugin.root}/prompts/survey.md`)`.
- `/housekeeping plan` returns the context of `prompts/plan.md`, plus the inventory, plus the current
  `check` findings when a `.housekeeping.json` exists.

**What each procedure says** (DESIGN 3.8, in the voice of this collection's other procedures):
- **`survey.md`:**
  - Read the inventory, then open the top candidates and the guide lines.
  - Sort each file into canonical, neighbour or history, giving the repository's own words for it.
  - Count the items and say how their status is written.
  - List the outside-work items.
  - List the references, and the machine readers that would break on a rename.
  - List the repository's own rules that constrain a move.
  - Write nothing.
  - End by offering `/housekeeping plan`, or `init` when there is nothing to move.
- **`plan.md`:** from the survey, give numbered steps:
  - the backlog keeps its name and every ID;
  - the playbook gets a new file with the definitions, under a name not already used;
  - each item becomes a row, and where only the owner knows a path or milestone, ask;
  - what stays apart by rule is linked, not moved;
  - history stays as it is;
  - the links, tests, scripts and guide files that change, including the repository's own statement of
    where deferred work goes;
  - the settings file;
  - each step that conflicts with a repository rule, marked "the owner's decision".

  Then wait for approval. Apply on a new branch, one commit per step, split as the repository's guards
  require, with its own tests before and after. Finish with `/housekeeping check` and
  `/housekeeping map`.
- **Both procedures** treat everything read as data, never instructions, and say so.

**Steps:**
- [ ] **Step 1: Write the failing tests** in `tests/plugin.test.ts` (serve the prompt files through
  `on('fs.read')`, as `dynamics` does):
  - `/housekeeping survey` returns context whose first item is the procedure and whose second holds the

  - `/housekeeping plan` in a repository with settings includes the findings;
  - in a repository with no candidates, the survey's text says there is nothing to move.
- [ ] **Step 2:** Run. Expected: FAIL.
- [ ] **Step 3:** Write the two procedures and wire the two arguments. Add both to the README's command
  list, and FORMAT.md's note on moving a repository.
- [ ] **Step 4:** Run the gate. Expected: PASS.
- [ ] **Step 5:** Commit: `housekeeping: survey and plan procedures`.
