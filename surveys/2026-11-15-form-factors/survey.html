Where mod-af's plugins work across Claude

A survey of decide, detell, dynamics, housekeeping, loose-ends and route on every Claude surface: Claude Code in the terminal, desktop app, IDEs and on the web; Cowork; and claude.ai chat on the web, desktop and mobile. The second tab is the plan for the proposed changes, and what testing it showed.

The bottom line

  • On your computer, in Claude Code, all six work as built. That covers the terminal, the desktop app's Code tab, VS Code and JetBrains.
  • In Cowork and chat, none of them run. All six are built as mods, code that runs in Claude Code only. Cowork and chat can add a plugin from a GitHub marketplace, but load only its skills, commands and remote connectors, so each of these six would load empty.
  • Claude Code on the web is closer than the docs suggest. A test session there loaded the plugins synced from the claude.ai account, and decide's mod ran in it. So adding mod-af in claude.ai probably brings all six to cloud sessions. That, and whether their panels and status lines show there, still needs one check.
  • Today's only route in Cowork and chat is pasting a plugin's prompt.md into the conversation. Five plugins have one; housekeeping doesn't. Those pasted copies have drifted from the plugins they copy.
  • Most of the gap closes cheaply. decide, loose-ends and route are written procedures and need no code. Rebuilt as standard skills, each would work on every surface, from one file, with no copy to drift. detell can follow. dynamics and housekeeping depend on code, files and git, so they fit Claude Code best.

Why: what each surface loads

A plugin is a folder that can hold several kinds of part. Each surface loads a different subset, and skips the rest without warning.

Cowork and chat add plugins from Customize > Plugins, including a marketplace on GitHub such as mod-af's. A plugin added there also syncs to Claude Code on your computers. The docs say Claude Code on the web installs no plugins from a marketplace, from your settings or from a repository's settings. But the plugins on the claude.ai account did load there: the test session offered their skills and commands.

  • Skills in chat run in Claude's code sandbox, so "Code execution and file creation" must be turned on. On Team and Enterprise plans an owner controls it.
  • loose-ends in chat can list what to file, but not write it to a backlog file. A connector, for example to an issue tracker, could do the filing.
  • route in chat needs the state to be there: uploaded files, a GitHub repository synced to a project, or a connector.

Found along the way

  • The pasted versions have drifted from the plugins. Each prompt-only plugin holds its procedure twice: inside its code, and in prompt.md. The two copies share, in order, about two thirds to four fifths of their words (decide 74% of the plugin's text, loose-ends 66%, route 69%), and detell only 16%. For example, route's rule "a short honest list beats a long hedged one" is in the plugin and not in the pasted form. One skill file read everywhere would end the drift.
  • The repository's README overstates. It says "every plugin ships both ways", installed or pasted, but housekeeping has no prompt.md.
  • Plugins added in claude.ai sync to Claude Code on your computers, and the test showed the account's plugins in a cloud session as well. One install could then cover every surface you use, if the plugins are built from parts every surface loads.

Still unknown

Where the docs are silent, the answer has to come from trying it:

  • Whether mod-af, once added in claude.ai, reaches Claude Code on the web the way the account's other plugins did in the test session; and whether a mod's panels and status line show there.
  • Whether Cowork gives a skill a shell or the working folder's files: this decides dynamics and housekeeping there.
  • Whether the status line and toasts that housekeeping uses are drawn in the desktop app's Code tab. The docs confirm panels and bands there.
  • Whether a skill can be uploaded from the mobile apps (using one there is documented), and whether custom styles still exist in claude.ai: no current help article covers them.

Next steps

  1. Decide the direction. Should mod-af's plugins work beyond Claude Code? If yes, rebuild the three prompt-only plugins as skills first: the change is small and covers every surface.
  2. Try one end to end. Rebuild decide as a skill, add mod-af as a marketplace in claude.ai, and check it in Claude Code, Cowork, chat on the web and on a phone, and a cloud session. That settles most of the unknowns above at once.
  3. Then loose-ends, route and detell, each with its prompt.md made from its skill file, so the two cannot drift.
  4. Decide whether dynamics needs chat or Cowork. It is the largest port and the most useful outside Claude Code if people model systems in chat.
  5. Say plainly that housekeeping is for Claude Code, and correct the README's claim that every plugin ships both ways.

What the tests showed

  • The skill route works. decide, rebuilt as one skill file with no mod, ran in Claude Code from /decide and /decide:decide. When someone asked for help deciding, Claude used it unasked.
  • prompt.md can be written from the skill file, and a check fails on any copy that has drifted. Testing the check found a flaw in it, now fixed.
  • dynamics' checker and renderer run as plain scripts, without the plugin. A one-file build gives the same page, so a dynamics skill can carry them.
  • housekeeping's command-line tool runs in a cloud session.
  • One survey answer changed. Plugins do reach Claude Code on the web: the test session had the account's synced plugins, and decide's mod ran there. The Survey tab now says so.

Decisions for you

  1. Go beyond Claude Code? This is the survey's first step. Everything below assumes yes.
  2. Which wording to keep. For decide, loose-ends and route, the plugin's text and prompt.md differ. The prototype kept the plugin's text, which is the one Claude Code users get today.
  3. How readily Claude should use these skills unasked. The description decides it. In the test decide was used on "Help me decide: …" and not on a plain opinion question. Say if you want it used more often, or less.
  4. For dynamics and housekeeping: add skills beside the mods, or replace them? I propose keeping the mods in Claude Code, where they give permission prompts, panels and a status line, and adding skills for the other surfaces.

Each change

A. decide, loose-ends and route become standard skills

Steps

  1. Settle the wording (decision 2).
  2. Write skills/<name>/SKILL.md: the name, and a description in quotes that says what it does and when to use it. Then the opening line and the procedure.
  3. Delete hooks/register.ts and hooks/hooks.json, which make it a mod.
  4. Add the generator, tools/prompt-md.mjs, and write each prompt.md with it. Run it with --check alongside the tests, so a stale copy fails.
  5. Raise each version. Tell users the call is /decide, or /decide:decide when two plugins share a name, and that the brief now comes at once. As a mod, /decide first replied with one line, and the brief came on the next message.

Tested here

  • Passed/decide:decide and /decide, each with a question about mod-af: the full brief, with The decision, Options, Recommendation and What would change this. The runs cost $0.16 to $0.18 each.
  • Passed"Help me decide: should our team move its weekly planning meeting…", with no slash: Claude called the skill itself and gave the full brief.
  • As intendedAn opinion question ending "Keep it short.": Claude answered directly, without the skill.
  • PassedThe plugin validates. The stricter check for Anthropic's plugin directory asks only for an icon, which matters only if you submit it there.
  • FoundUnquoted, the description holds ": " and a strict YAML parser rejects it. Rule for every skill: quote the description.
  • PassedThe drift check passes on a fresh copy. It fails after a hand edit of prompt.md, and after an edit of the skill file. It passes again once the copy is rewritten. It stops on a plugin with no skill yet, such as route today.
  • Found, fixedThe check first took the plugin's name from its folder, so a copy in a folder named decide-skill failed. It now reads the name from the plugin's own plugin.json.
Effort
About an hour per plugin
Risk
Low. A description can make Claude use the skill too often or too rarely.
Still to test
Cowork, chat, the phone, and cloud sessions through claude.ai (card F)

B. detell becomes two skills

Steps

  1. skills/detell/SKILL.md holds the loop procedure and the checklist of tells, with a "last refreshed" date above the checklist.
  2. skills/detell-refresh/SKILL.md fetches Wikipedia's "Signs of AI writing", adds what is new to the checklist and moves the date.
  3. The 14-day reminder becomes one line in the skill: if the date is more than 14 days old, say so and offer the refresh. Nothing has to be stored.
  4. Delete the mod and write prompt.md with the generator. Today the pasted copy shares only 16% of the plugin's words, so this is the largest correction of the four.

What planning it showed

  • FoundThe checklist must stay inside SKILL.md. The generator copies only that file, so a checklist kept in a separate file would be missing from prompt.md. The alternative is to teach the generator to include it.
  • LimitIn chat and Cowork a refresh cannot save the new list back to the plugin. It holds for that conversation only. A lasting refresh is a change committed to mod-af. A refresh also needs web access.
Effort
Half a day
Risk
Medium: the refresh works differently on each surface
Tested here
Not on its own. It uses the same mechanism as decide.

C. dynamics gains a skill that carries its checker and renderer

Steps

  1. Add scripts/dynamics.mjs, one file of plain JavaScript built from the checker and renderer, with two commands: check a model, and draw its page.
  2. Commit the built file, so nothing needs installing. Add a test that fails when the built file is stale or draws a different page.
  3. The skill says: where there is a shell, run the script. In chat, work from uploaded or GitHub-synced files, and publish the page as an artifact.
  4. Keep the mod in Claude Code. The skill says to use the mod's tools when they are there.
  5. The mod decides which files may be read, and asks before reading. The script must keep the same rule. Moving the rule into the shared code, rather than copying it into the script, stops the two from drifting.

Tested here

  • PassedThe checker and renderer import nothing from the plugin platform, only each other.
  • PassedRun as a plain Node script on the plugin's worked example: the check passed and found 7 loops, and the page was drawn: 54,250 bytes, titled "Job Runner Dynamics".
  • PassedA one-file JavaScript build of the same code, made with bun, drew a byte-identical page.
Effort
A few days
Risk
Medium to high. The file-reading rule is a second place that must agree. Chat's Node version is unknown. The reviewer agents don't load in chat.
Still to test
Node in chat's sandbox; a shell in Cowork

D. housekeeping stays Claude Code first

Steps

  1. Say in its README that it is built for Claude Code on a computer, and that the Node command is the route elsewhere.
  2. Optionally, add a skill that runs node housekeeping/cli.ts where there is a shell and a clone. A repository first needs its .housekeeping.json. The init command writes it in Claude Code, or you can write it by hand from FORMAT.md.

Tested here, in a cloud session
